# Respaldo CSV del prototipo y del backend

En **Configuración → Respaldo de datos**, el administrador puede descargar un archivo `respaldo-completo-cabello-AAAA-MM-DD.csv`. Es un CSV legible directamente, sin contraseña ni cifrado. Los CSV de Compras, Ventas, Inventario, Proveedores y Deudas sirven para consulta; el respaldo integral reúne todas las secciones aunque haya filtros activos.

El intervalo del recordatorio se configura en días (1 a 365, inicialmente 7). El aviso aparece si nunca se confirmó una copia o si transcurrió el intervalo desde la última descarga confirmada. Después de descargar, el administrador debe comprobar que el archivo está guardado y pulsar **Confirmar archivo guardado**. El prototipo conserva únicamente el intervalo y la fecha de confirmación en el almacenamiento de este navegador para mantener el recordatorio tras una recarga. El backend deberá persistirlos por sucursal y usuario administrador para que se compartan entre dispositivos. La aplicación no puede verificar por sí sola que el archivo continúe en la computadora.

## Contenido

El CSV integral tiene las columnas `Tipo de registro`, `Identificador` y `Datos completos JSON`. Separa columnas con punto y coma y codifica el texto en UTF-8 con BOM. La primera fila de datos es un manifiesto con versión, fecha de exportación, moneda, unidad, zona horaria y cantidad de registros de cada tipo. Después incluye configuración, categorías, longitudes, lotes iniciales, productos, proveedores, compras, ventas, deudas, empleados y asignaciones de coste calculadas. Los objetos de compras, ventas, deudas y empleados incluyen sus líneas, pagos e historiales completos. Los identificadores y fechas se conservan tal como están en el prototipo.

El prototipo ya registra recepciones, entregas parciales y pagos propios dentro de cada compra o venta. Los movimientos, sus anulaciones y las correcciones o anulaciones de pagos quedan incluidos en el JSON de la operación. El manifiesto del prototipo usa la versión 2 del formato.

El backend, que comienza con datos nuevos, exporta e importa la versión 3: conserva las mismas tres columnas legibles, pero cada fila corresponde a un registro de una tabla de PostgreSQL. Incluye lotes, asignaciones de costo, pagos, deudas e historiales sin recalcularlos al exportar. La versión 2 no se importa automáticamente en el backend porque representa las entidades de otra manera.

La futura apertura de inventario para el stock físico anterior al sistema aún no está implementada en el backend ni en su CSV versión 3. Antes de usarla en producción, se ampliarán conjuntamente la exportación, la validación y la restauración para conservar el evento de apertura, sus lotes, costos, orden e historial; el formato tendrá una versión nueva o una compatibilidad explícita con la versión 3.

Las contraseñas de empleados no se exportan. En el prototipo solo existen en memoria y nunca deben aparecer en un CSV. Las sesiones activas tampoco se exportan. El CSV versión 3 del backend restaura los datos del negocio. Si todavía existe la base de datos anterior, se conservan los hashes de contraseña actuales y la obligación vigente de cambiar la contraseña de las cuentas que correspondan al mismo identificador estable, incluido el administrador; el CSV no contiene contraseñas ni hashes. Para un empleado presente en ambas bases, el estado desactivado prevalece si aparece en cualquiera de las dos, de modo que restaurar una copia antigua no reactive su acceso. En una recuperación sin base anterior, el administrador obtiene acceso mediante el comando privado del VPS ya previsto. Un respaldo nativo de PostgreSQL puede mantenerse como vía técnica adicional.

El CSV contiene datos personales y comerciales legibles. Guardarlo en un lugar al que solo tenga acceso el administrador. Los respaldos antiguos con extensión `.csv.enc`, si existen, pueden descifrarse con `scripts/decrypt-backup.mjs` para consultarlos; si contienen el formato del prototipo, no sirven como importación directa al backend.

## Restauración en el backend

El backend acepta la versión 3, valida el manifiesto y las referencias mediante una vista previa reversible, e importa todo en una transacción. El inventario se restaura desde los lotes y consumos guardados; no se vuelven a aplicar compras y ventas al stock. Se conservan identificadores, estados, fechas, pagos e historiales. Las cuentas sin credencial conservable de la base anterior reciben una contraseña aleatoria desconocida: el administrador deberá restablecer la de cada empleado; si el administrador es nuevo, recuperará su acceso con el comando privado `recover`.

La API de restauración es exclusiva del administrador y ya dispone de vista previa con formato, versión, fecha, referencias y cantidades. Antes de ejecutarla se debe mostrar en el panel una advertencia clara de que se reemplazarán todos los datos incluidos en el CSV y se perderán los movimientos posteriores a la fecha de la copia; después se pedirá una confirmación explícita. No se combinan registros del archivo con los actuales. El reemplazo se ejecuta en una transacción, y las restauraciones completadas quedan registradas en una bitácora técnica. La interfaz del panel todavía debe conectarse con estas rutas.

Después de validar el archivo y antes de habilitar la confirmación final, la API genera un CSV del estado actual. El administrador debe confirmar que quedó guardado. Si los datos cambian después de esa copia, la restauración se rechaza y debe repetirse la preparación. Durante el reemplazo se bloquean las tablas del negocio para impedir movimientos simultáneos.

La restauración no cerrará automáticamente las sesiones abiertas. En cada solicitud posterior, el backend comprobará contra el estado restaurado que la cuenta vinculada a la sesión todavía existe, está activa y conserva permiso para la acción. Una sesión de una cuenta eliminada o desactivada no concederá acceso, aunque la sesión aún esté almacenada. Las cuentas que sigan activas continuarán con sus sesiones normales. Un restablecimiento de contraseña realizado por el administrador sí cerrará inmediatamente todas las sesiones del empleado afectado.


Una copia semanal guardada únicamente en la computadora del administrador puede perderse junto con esa computadora y puede tener hasta siete días de antigüedad. La copia automática incluida de OVHcloud conserva solo la última copia durante 24 horas.
Con la frecuencia inicial de siete días, el administrador conservará manualmente las últimas cuatro copias descargadas. Solo eliminará la más antigua después de comprobar que la nueva quedó guardada. Si cambia la frecuencia, deberá revisar cuánto tiempo histórico cubren esas cuatro copias.
