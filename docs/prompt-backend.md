# Prompt para implementar el backend

Copia el bloque siguiente en una sesión de desarrollo con acceso a este repositorio. Debe leerse junto con [decisiones-backend.md](decisiones-backend.md), [respaldos-csv.md](respaldos-csv.md) y [guia-backend.md](guia-backend.md).

```text
Actúa como desarrollador principal de La Magia del Cabello. Trabaja en el repositorio privado actual, que contiene un frontend Angular y un prototipo en memoria. Primero inspecciona el código, los modelos y los documentos docs/decisiones-backend.md, docs/respaldos-csv.md y docs/guia-backend.md. Implementa en este mismo repositorio un backend real dentro de backend/ con Java, Spring Boot y PostgreSQL. Propón cualquier decisión de negocio aún ambigua en una sola ronda de preguntas; no reabras las ya resueltas. Haz entregas pequeñas, revisables, y explica cada cambio.

ALCANCE Y TECNOLOGÍA
- Una sola sede, un administrador y empleados; hasta unos cinco empleados y unas 800 transacciones/año al comienzo. No crear por ahora sucursales ni superadministrador, pero usar identificadores estables y límites claros para facilitar esa evolución.
- Aplicación siempre conectada. Desarrollo y comprobaciones locales. Producción única en OVHcloud VPS-1. Monorepositorio privado actual; Angular, Spring Boot y PostgreSQL mediante Docker Compose en el mismo VPS, con proxy HTTPS y frontend y /api bajo el mismo origen.
- Continuar desde la base local ya creada en backend/ con Java 21, Spring Boot 4.1.1 y PostgreSQL 18.6; revisar actualizaciones y compatibilidad antes de producción. Usar Spring Web, Validation, Security, Spring Session JDBC, PostgreSQL, Flyway y Actuator. Toda evolución de base de datos va por migraciones. No poner credenciales en Git, imagen o código.
- En producción cargar categorías y longitudes actuales y ningún registro de demostración. El stock real anterior al sistema se incorporará mediante una apertura de inventario antes de registrar operaciones. El frontend en memoria es referencia visual y funcional, no base de datos para migrar.

MODELO Y OPERACIONES
- Catálogos modificables de categorías y longitudes; impedir eliminación si están en uso. Inventario por combinación de categoría y longitud, visible si hubo compras o una apertura de inventario. Compras referencian proveedor mediante ID estable y muestran siempre su nombre vigente; ventas guardan solo nombre de cliente.
- Cada compra y venta tiene varias líneas con combinación, gramos acordados y precio por gramo. Gramos, precios e importes tienen dos decimales como máximo. Rechazar más decimales sin redondeo silencioso. Multiplicar cada línea y redondear su importe con HALF_UP a dos decimales; sumar importes de línea redondeados. Guardar fecha de operación, fecha/hora real de cada movimiento de recepción o entrega y momento de registro en el sistema por separado, incluidos varios movimientos el mismo día. Si se registra tarde, pedir fecha y hora reales. La hora se muestra solo en el detalle de la transacción.
- Estados Pendiente, Confirmado, Anulada. Cada recepción o entrega parcial mueve solo la cantidad real; la operación sigue Pendiente y muestra progreso por línea hasta completarse. Al anular una operación, cancelar solo el saldo sin cumplir y conservar movimientos efectuados. Editar solo cantidades no cumplidas; corregir movimientos ya realizados (fecha, hora o peso) únicamente con motivo obligatorio, historial antes/después, validaciones y recálculo de stock, reservas, costos y márgenes. Permitir anular un movimiento registrado por completo por error, sin borrarlo y solo si sus efectos pueden revertirse coherentemente. Si una corrección/anulación cambia el progreso completo, ajustar el estado. Toda edición exige motivo. Conservar actor y momento en el historial.
- Una venta pendiente reserva primero stock físico y después compras pendientes. Si una o varias líneas necesitan cabello por recibir, pedir aceptación y dejar la venta Pendiente. Cuando llega el cabello, mantenerla Pendiente hasta que el administrador registre la entrega real al cliente. Si alguna línea no tiene respaldo ni contando entradas pendientes, rechazar la venta completa e informar faltantes por tipo y origen. No permitir stock físico negativo ni reservas sin respaldo. Usar transacciones, bloqueo/control de versión e idempotencia para evitar carreras y solicitudes repetidas.
- Cada recepción crea un lote con costo por gramo; cada entrega consume los lotes más antiguos en orden temporal. Mantener asignaciones trazables y recalcular costos e indicadores históricos cuando una corrección de fecha, hora, cantidad o precio cambie el orden o valor de los lotes. Rechazar correcciones que harían imposible reconstruir entregas pasadas. El detalle de inventario muestra movimientos de compras y ventas como sumas y restas; en escritorio muestra columnas suficientes y en móvil un desglose dentro del detalle.
- Implementar una apertura de inventario exclusiva del administrador con una única fecha y hora de corte, anterior a las primeras operaciones. Registrar el peso físico y costo por gramo de cada partida por categoría y longitud; permitir varios lotes del mismo tipo cuando se conozcan antigüedades o costos distintos e indicar si el costo es estimado. Presentar una vista previa antes de confirmar. Crear lotes vendibles sin crear compras, proveedores, pagos ni deudas ficticios. Mostrar la apertura en el detalle de inventario y auditar correcciones con motivo y validación de ventas históricas. Su costo se usa para margen bruto cuando se vende; su valor no cuenta como compras del periodo. Incluir sus datos en CSV, restauración y comprobaciones.
- Compras y ventas tienen pagos, anticipos y saldos propios. Cada pago guarda fecha, importe, método Efectivo/QR/Transferencia/Otro y referencia opcional. Permitir corregir o anular pagos con motivo e historial antes/después; un pago anulado no cuenta en el total. El total exigible nunca puede quedar por debajo de lo pagado vigente. Si al anular un saldo pendiente los pagos superarían la parte cumplida, bloquear y explicar; no diseñar flujo de excedentes ahora. Deudas son movimientos de efectivo ajenos a compras y ventas, con su historial propio, sin vínculo automático.
- Reportes por días, semanas o meses reconocen compras e ingresos por cantidades efectivamente movidas, aunque la operación siga Pendiente. Mostrar cero en periodos sin movimientos. El costo de venta proviene de lotes y el resultado es margen bruto; pagos y anticipos no determinan ingresos del reporte. No incluir facturas fiscales, adjuntos ni resultado neto.

SEGURIDAD Y USUARIOS
- Inicio con usuario y contraseña. Sesiones del servidor persistidas en PostgreSQL, que sobreviven cierre del navegador y reinicio; expiración tras 24 horas de inactividad o 7 días absolutos desde el inicio. Cookie Secure, HttpOnly y SameSite; protección CSRF para escrituras. Comprobar identidad, actividad de cuenta y rol en cada petición.
- Administrador: todas las funciones y gestión de empleados. Empleado: solo lectura de Inventario, Compras, Ventas, Reportes y perfil; puede cambiar únicamente su contraseña indicando la actual. Sin acceso a Inicio, Proveedores, Deudas ni operaciones de escritura. Autorización en el servidor, no solo menús del frontend.
- Cuenta de empleado: usuario, contraseña, nombre completo, CI, nacimiento, celular, activo/desactivado e historial. Contraseñas mínimo 8 caracteres, hash robusto; creación y restablecimiento generan clave temporal que obliga a cambiarla antes de acceder al resto de la API. Desactivar o restablecer revoca inmediatamente todas las sesiones de esa cuenta. Cambiar contraseña propia mantiene solo la sesión actual. No guardar contraseñas anteriores/nuevas en historial. Aplicar esperas progresivas a intentos fallidos, sin bloqueo permanente.
- Crear y recuperar el primer administrador con comando privado en el VPS, no endpoint público; pedir interactivamente el nombre de usuario y contraseña (entrada oculta). El administrador puede cambiar su propia contraseña con la actual y revocar sus otras sesiones; la recuperación privada revoca todas. Documentar invocación segura en Docker Compose.

RESPALDOS Y RESTAURACIÓN
- Exportar CSV integral versionado, legible y descargable solo por administrador. Incluir todos los datos originales para reconstruir catálogos, proveedor, operaciones, líneas, movimientos, lotes/asignaciones, pagos, deudas, usuarios sin hashes, configuración e historiales. Excluir contraseñas, hashes y sesiones. Mantener compatibilidad explícita o una migración documentada desde el formato de prototipo v2; no declarar restaurable un formato que no pueda importarse realmente.
- Recordatorio inicial cada siete días, modificable en Configuración; descarga manual a la computadora del administrador y conservación de cuatro copias. Advertir si cambiar la frecuencia amplía el máximo tiempo de datos que podrían perderse. No cifrar el CSV por requisito del cliente.
- Restauración desde panel: validar archivo entero, referencias, precisión, versión y coherencia sin modificar datos; mostrar vista previa y advertencia; descargar una copia previa del estado actual y exigir confirmación de que se guardó; reemplazar todo en una transacción y registrar resultado. Durante la sustitución impedir escrituras. Si falla, dejar el estado anterior completo.
- Conservar hashes y estado de cambio forzoso vigentes de cuentas coincidentes por ID estable si la base previa existe. Si una cuenta estaba desactivada en cualquiera de los dos estados, no reactivarla con una copia antigua. Las cuentas sin credencial conservable necesitan clave temporal. Una restauración no cierra sesiones por sí sola; cada petición comprueba permisos actuales. Documentar recuperación cuando la base anterior se haya perdido.

API, FRONTEND Y ENTREGA
- Diseñar contratos de API claros para autenticación, catálogos, proveedores, inventario, compras, ventas, movimientos parciales y sus correcciones, pagos, reportes, deudas, empleados, configuración, respaldo y restauración. Añadir validación de entrada, paginación, filtros, ordenación, errores legibles y un contrato documentado.
- Sustituir gradualmente DemoStore en Angular por servicios HTTP sin perder el diseño móvil/escritorio. Estado, stock, saldos, costos y permisos son calculados/validados por backend. Mostrar errores de faltantes y conflictos; desactivar envíos duplicados. Mantener el progreso e historiales en detalles.
- Crear comprobaciones automáticas pertinentes para precisión monetaria, reservas, operaciones parciales, orden de lotes, concurrencia, correcciones retroactivas, permisos, sesiones y restauración real. Ejecutarlas localmente y en CI antes de aprobar cada cambio. No publicar código sin revisión del resultado.
- Preparar Docker Compose de producción con proxy HTTPS, Angular, API y PostgreSQL en el mismo VPS; exponer solo 80/443. Usar subdominio gratuito al inicio. Desplegar automáticamente los cambios aprobados al incorporarse a main, con migraciones, verificación de salud y procedimiento de reversión. En GitHub Free con repo privado, no asumir que se pueden imponer aprobaciones/protecciones de rama: revisar y aprobar manualmente antes del merge a main, o documentar un plan de pago si se requiere enforcement técnico.
- Entregar README de desarrollo local, variables de entorno de ejemplo sin secretos, migraciones, documentación de API, comandos de Docker, guía paso a paso para comprar/configurar el VPS cuando llegue esa fase, procedimiento del primer administrador, operación de respaldos/restauración y criterios de aceptación. No comprar VPS, cambiar DNS, fusionar a main ni desplegar producción sin aprobación expresa del usuario sobre el resultado concreto.
```
